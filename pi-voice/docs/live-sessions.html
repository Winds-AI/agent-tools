GPT-Live sessions — events, channels & harness timelines

Reference for pi-voice. Facts from OpenAI's Live sessions & delegation guides (fetched 2026-09-13) plus the extension's own behavior.

The three text-append channels

ChannelDocumented use caseSpoken?Cap
session.instructions.append"System-level instructions for the live model, such as a greeting, disclosure, or direction to stop speaking." Can interrupt current speech (e.g. guardrail redirects).shapes speech; may interrupt500 tokens per append; requires delegation_id (null = session-wide)
session.thinking.append"Factual context without asking the model to say it immediately" — quiet context for later answers. Documented pattern: background progress ("Checking Thursday availability…"), UI/state summaries. Not a privacy boundary.no (not immediately)
session.commentary.append"Information for the model to say aloud" — results of delegated work. The model is "trained to paraphrase the appended text." Send only after actions verifiably succeed.yes (may paraphrase)
pi-voice uses commentary for Pi's result (both in-session and after reopen) and nothing else — no thinking, no instructions.

Why every append needs delegation_id

The field routes the context: pass the delegation's ID when the append is an update about that delegated task; pass null for general session-wide context. null itself is meaningful, so the field is mandatory. A non-null ID must name a known client delegation (IDs from session.delegation.created are opaque — return unchanged). Even with an ID, instructions still apply to the live session — an ID never becomes a separate backend prompt. pi-voice appends results session-wide (null) because Pi's result usually arrives after the original session closed.

Timeline 3 — client vs Responses delegation

Client delegation (pi-voice uses this): model emits delegation.created (target: client) → your code builds the request, runs the agent, enforces permissions, then feeds results back with delegation-scoped appends (commentary = spoken, thinking = quiet). You own the context.

Responses delegation: the Live model itself calls a configured Responses backend model (chosen at session creation); backend events arrive nested in response.event envelopes; function results go back via response.item.create + an explicit response.create (appending a function result does NOT auto-continue). You only implement custom functions and approvals. Mode is fixed at session creation — switching mid-session fails with immutable_field_update.

How this differs from a normal text LLM call

  • Billed by duration ($0.05/min, per second, silence included) — not by tokens. Architecture exists to minimize connected time.
  • Full-duplex — the model listens while it speaks; there are no request/response turns, and no turn-completed event.
  • Audio-first — output is speech; transcripts are unaligned byproduct fragments. Audio deltas have no done marker (hence energy-based activity detection).
  • Commentary may be paraphrased — never rely on verbatim playback; the terminal holds the real answer.
  • Context is staged — a seeded history at connect (≤128 msgs / 8,192 tokens, no system role) + three mid-session append channels (≤500 tokens each, delegation_id mandatory).
  • 128K session window with automatic compaction — old history is summarized by the API as it fills.
  • Muting ≠ pausing — muting the mic does not stop inference, delegated work, or generated speech.
  • session.closed is the only finalization proof — usage.updated values are cumulative snapshots.
  • Audio + text only — no image or file input on this model.
